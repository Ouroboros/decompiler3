# 脚本工具链重新设计

状态：方案阶段，尚未实现。在新管线追平旧管线之前（第 10 节），现有管线仍然是参照标准。

## 1. 目标

1. **完整**：脚本的每一层表示都完整，从而可以反编译、人工修改、再编译回去。
2. **多 VM**：框架分成和 VM 无关的**核心**，以及每种 VM 各一份的**目标层**。支持一种新的脚本 VM（比如以后的 ED12）时，只需要新写一份目标层，核心不用改，就能输出同样的高级语言脚本。
3. **双向**：反编译和编译共用同一套核心。同一份高级语言源码，可以编译到任何一个提供了该脚本所用功能的目标 VM。

本文覆盖反编译部分，所有接口都同时定义了逆方向，以后加入编译器时不必改动各层的表示和接口。

继续作为权威依据的有：`falcom/ed9/spec/vm_spec.md`（已对照 `ed9_crack.exe` 的汇编核对）、`falcom/ed9/vm_values.py`、`tools/diffcheck` 里的字节码参照解释器，以及 `scena` 的 88 个脚本和 3 份测试 DAT。

## 2. 原则

| # | 原则 | 带来的要求 |
| --- | --- | --- |
| P1 | 每一层表示，按信息契约（第 4 节）都是完整的 | 任何一层都能单独生成后端，不需要解析器 |
| P2 | 每一步变换都有逆变换或校验手段 | 读 / 写、解码 / 编码、提升 / 下降、结构化 / 展平 |
| P3 | 每个事实只定义一次 | 一份二进制 schema 同时负责读和写；一张指令表同时负责解码、编码和解释执行；一套值语义；平坦 IR 和结构化 IR 共用一套表达式节点 |
| P4 | 不存在可以忽略的节点 | 行号和调试日志都是正式语句；任何 pass 都不能把它们当成空操作或删掉 |
| P5 | 验证是管线的一部分 | 每一阶段都有往返检查、审计或解释器；检查模式下，每个 pass 跑完都审计一次 |
| P6 | 核心不含任何 VM 概念 | 寄存器、全局变量、syscall、字长、值的编码、调用约定都由目标层声明；核心只通过目标接口（第 3 节）使用它们 |

## 3. 核心与目标层

```
             ┌──────────────── 目标层（每种 VM 一份，例如 ed9/）────────────────┐
bytes  ⇄  L0 文件镜像  ⇄  L1 指令  ⇄（提升 / 下降）⇄
             └────────────────────────────────────────────────────────────────┘
                         ┌──────────── 核心（和 VM 无关）────────────┐
                    ⇄  L2 平坦 IR（⇄ SSA）  ⇄  L3 结构化 IR  ⇄  后端 / 前端（TypeScript 等）
                         └────────────────────────────────────────────┘
```

### 3.1 核心负责

`Module` 容器；L2 和 L3 的节点、SSA、各种 pass、结构化、命名；后端（高级语言输出）和以后的前端（高级语言输入）；契约审计框架；一个按目标语义参数化的 L2 / L3 解释器；验证框架。

### 3.2 目标层必须实现的接口

| 接口 | 内容 | ED9 的对应 |
| --- | --- | --- |
| `ImageFormat` | `read(bytes) -> Image`、`write(Image, layout) -> bytes`，基于声明式 schema | `#scp` 文件头、函数表、全局变量表、调试信息 |
| `InstructionSet` | 指令表：解码、编码、格式化，以及按 VM 规格实现的字节码参照解释器 | 41 条指令，`vm_spec.md` |
| `ValueSemantics` | 有哪些值类型和字面量形式；每个运算符的求值；真值判断；"两个常量是否同一个值"；哪些化简在什么类型下成立 | `vm_values.py`：30 位整数、截掉低 2 位的浮点、Raw、字符串偏移、类型错误路径 |
| `StorageModel` | 声明有哪些存储类（名字、编号范围、跨调用时是否保留、能否取地址） | 16 个寄存器、全局变量表、栈上参数和局部变量、栈地址 |
| `CallModel` | 声明有哪些被调用者种类和它们的键（比如"本地函数：函数号""外部模块：模块 + 函数""宿主调用：两个编号"），以及每种调用可能改写哪些存储 | `CALL`、`CALL_SCRIPT`、`SYSCALL`；调用可能改写任意寄存器和全局变量，以及指针参数指向的位置 |
| `Lifter` / `Lowerer` | L1 → L2 的提升，L2 → L1 的下降；包括调用约定（参数顺序、返回值通道） | 第 1 个参数最后压栈；返回值放在 `REGS[0]` |
| `MetadataSchema` | 本 VM 特有、核心要原样保存的元数据，定义成带类型的附加项，挂在模块、函数或语句上 | `dword_14`、`name_hash`、`byte06`、参数标志原值、调试信息记录 |
| `Signatures` | 宿主调用和包装函数的名字、参数类型、默认值 | syscall 包装函数、函数表里的参数类型 |
| `BackendHints` | 本 VM 的值类型和被调用者，在各个后端里怎么书写 | 例如 Raw 写成 `raw(0)` |

核心里的节点只使用这些声明出来的东西：`Load(storage, key)`、`Store(storage, key, value)`、`Call(callee, args)`（`callee` 是目标层声明的被调用者种类加上它的键）、`Const(kind, value)`（`kind` 是目标层声明的值类型）。核心里不出现 `REGS`、`syscall`、`WORD_SIZE` 这类 VM 专用的名字。

### 3.3 支持一个新 VM 需要做的事

只新写一个目标包，实现第 3.2 节的全部接口，并提供该 VM 的规格文档和测试语料。核心、后端和验证框架都不改。核心要是缺某种能力（比如间接跳转、跳转表），按"补核心的通用能力"处理，并且必须先用测试 VM（第 7 节 V6）证明它和具体 VM 无关。

### 3.4 编译到不同的 VM

前端把高级语言解析成 L3，核心把它展平成 L2，再交给目标层的 `Lowerer`、`InstructionSet`、`ImageFormat` 依次下降、编码、写出。如果源码用到了目标 VM 没有的值类型、存储类或被调用者，在下降之前就报错，不生成近似的代码。

## 4. 信息契约

### 4.1 核心契约（所有 VM 共用）

| 范围 | 内容 |
| --- | --- |
| 模块 | 函数表（顺序、名字、参数的类型和默认值）、全局存储表（名字、类型） |
| 代码 | 行为；行号及其原始地址；调试日志语句；带值类型的常量的精确值 |

### 4.2 目标扩展契约（每个 VM 由 `MetadataSchema` 声明，核心原样保存）

ED9 的扩展项有：文件头字段 `dword_14`；函数的 `name_hash`、`is_common_func`、`byte06`、参数标志的 32 位原值；调用调试信息原样保存（包括参数个数为 0 的条目）。Raw 和整数的区别属于 ED9 的 `ValueSemantics`，通过常量的值类型保存。

### 4.3 可以重新生成的信息

代码和栈的布局（偏移、标签、栈槽、从未被读到的栈上值），调用序列中固定的部分（ED9 的 `PUSH_CURRENT_FUNC_ID`、`PUSH_RET_ADDR`、`PUSH_CALLER_FRAME`），字符串和各种表的布局。走不到的死代码只在 L0 和 L1 保存（决定 D1）。

## 5. 分层

### L0 文件镜像（目标层）

`Image` 包括：本 VM 的各种表、字符串池、每个函数的代码字节，以及单独存放的 `Layout`（各段的顺序、偏移、字符串的位置）。

- 每种记录只用一份声明式的 schema 描述，同时驱动读和写。
- 用原布局写回时字节完全相同；用重新生成的布局写回再读出时，`Image` 相同。
- 整个文件读一次进内存再解码。

### L1 指令（目标层）

每个函数的全部字节范围，从入口一直线性解码到下一个函数，跳转目标转成标签；CFG 标出走不到的指令。

- 一张指令表同时驱动解码、编码、格式化和参照解释器。
- 每个函数都满足 `encode(decode(code)) == code`。

### L2 平坦 IR（核心）

没有栈，基于 CFG。语句有：`Assign`、`Store`、`Call`、`If`、`Goto`、`Return`、`Line`、`Log`。表达式有：常量、变量、`Load`、取地址、运算符。存储类、被调用者种类、值类型和运算符都由目标层声明。

- SSA 形式用的是同一套节点，用于分析，用完再解构回来。
- 常量折叠、类型判断和代数化简一律询问目标层的 `ValueSemantics`。
- 调用对存储的影响来自目标层的 `CallModel`，核心据此判断调用前后哪些值不能复用。

### L3 结构化 IR（核心）

由 `Block`、`If`、`While`、`DoWhile`、`Switch`（支持多值 case）、`Break`、`Continue`、`Return` 组成的树，叶子就是 L2 的语句和表达式本身，是同一批节点类，不是复制品。

- 结构化使用后支配节点（即现有 `structural_analysis.py` 的算法），共享代码显式复制；复制出来的 `Line` 语句保留原来的地址。
- 定义 L3 → L2 的展平，这样结构化的结果能被校验，也能编译回去。
- 可读性相关的 pass 在 L3 或 L2 上运行，受同样的审计约束。

### 后端和前端（核心）

后端负责翻译 L3 层的 `Module`，必须说明每一项契约内容在输出里怎么表示；目标层的值类型和被调用者，通过 `BackendHints` 决定写法。TypeScript 后端保留回读检查（`ts_parse.py`），以后它就是编译器前端的起点。

## 6. Pass

```
class Pass:
    preserves: set of contract items      # 检查模式下，pass 跑完后审计这些项
    def run(self, module) -> module
```

- pass 可以移动或复制 `Line` 和 `Log` 语句，但不能删除它们。审计时，行号按"(地址, 行号)"集合比较，日志按多重集比较。
- 目标扩展的元数据对 pass 是不透明的，只能原样搬运。
- 检查模式下，每个 pass 跑完都执行契约审计，并可选地执行解释器，所以信息丢失或错误改写能归到具体的某一个 pass。

| 检查 | 范围 | 证明什么 |
| --- | --- | --- |

## 8. 和现有设计的对比

现有设计一栏的数据来自现有代码和 `scena` 的 88 个脚本。新设计一栏是设计目标，要等原型实测（第 9 节）。

| 维度 | 现有设计（实测） | 新设计（目标） |
| --- | --- | --- |
| 多 VM 支持 | ED9 的概念写死在通用层：`ir/` 和 `codegen/` 里，syscall 相关 120 处、27 个文件；寄存器 101 处、23 个文件；全局变量 77 处、19 个文件；跨脚本调用 84 处、23 个文件；栈字长 `WORD_SIZE` 11 处、3 个文件。只有常量折叠一个扩展点（`ConstantFolder`）。支持新 VM 要改通用节点类和代码生成 | 核心不含 VM 概念；新 VM 只实现目标接口；由 V6 证明 |
| 编译到不同 VM | 没有编译器；IR 是单向的 | 同一套核心，下降和编码由目标层负责；目标不支持的功能在下降前报错 |
| 信息完整性 | 全局变量名 5 个全错；跳过 112,461 条调试信息；Raw 标记在 LLIL 之后丢失；HLIL 里至少丢了 572 个行号；参数标志在 HLIL 里丢失；`DEBUG_LOG` 在 lifter 里丢失 | 每一层的契约审计都是零差异（V2） |
| 往返 | 没有写出器和编码器：0/88 | 88/88 逐字节相同（V0、V1） |
| 换节点类型的转换次数 | 6 次（模型 → 指令 → LLIL → MLIL ⇄ SSA → HLIL → TypeScript），每一次都可能丢信息 | 3 次（文件镜像 → 指令 → L2；L2 → L3 共用节点；L3 → 后端） |
| 节点类型数 | LLIL 50、MLIL 57、HLIL 32，共 139 个 | L2 和 L3 共用一套表达式；总数估计少于 60 个 |
| 行为验证 | 字节码 ≡ HLIL ≡ TypeScript；22,118 / 22,118 通过，块覆盖率 99.66% | 字节码 ≡ L2 ≡ L3 ≡ 后端，通过率和覆盖率至少相同 |
| 出错定位 | 只到 HLIL 的 pass；MLIL 及更早的问题只能报"MLILToHLIL (or MLIL)" | 能定位到具体的层和 pass（V4） |
| 值语义 | SCCP 和检查器用 `vm_values`；其他 pass 按 Python 的值推理 | 全部询问目标层的 `ValueSemantics` |
| 指令层是否忠实 | 反汇编器拆分基本块时，会在 `offset - 1` 处插入长度为 0 的伪 `JMP`（最大的 3 个脚本里有 595 条），指令列表不等于字节码 | L1 只包含真实解码出的字节；fallthrough 用 CFG 边表示，不是指令 |
| I/O | `FileStream` 直接读文件，几乎每读一个值都要 `seek`，而每次 `seek` 都要通过 9P 从 `/mnt/d` 重新填充缓冲 | 整个文件读一次，从内存解码 |
| 可读性（TypeScript） | `let` 共 58,764 个，其中 54,317 个是寄存器临时变量；22,719 处通过临时变量返回 | 不比现在差；临时变量在 L2 去掉 |
| 速度 | 见 8.1 节 | 不比现在慢；从内存解析 |
| 开发成本 | 已经存在 | 追平之前都是新增工作量，这是新设计唯一会输的一项 |

## 9. 推倒重建之前的评估

1. 在 `c1010`、`c1020`、`m7200`（共 167 个函数）上，把整条链从 L0 做到 TypeScript，做出原型；同时写一个测试用的小型 VM 目标，验证目标接口（V6）。
2. 在同一批函数上，把第 8 节的每一行指标都对新旧两种设计各测一遍。
3. 只有当新设计除开发成本外每一项都不比旧设计差，并且在多 VM 支持、完整性、往返和定位能力上明显更好时，才推倒重建；否则就在现有管线上逐处修补。

## 10. 迁移

- 新的核心包和 ED9 目标包放在本仓库里，和现有包并列；整个过程中，现有管线、检查器和测试语料都保持可用。
- 已经验证过的算法直接移植，不重新发明：后支配汇合点、共享代码复制、带多值 case 的 switch 还原、按 VM 语义的常量折叠（改为通过 `ValueSemantics`）、按 VM 顺序的参数编号（改为 ED9 目标层的调用约定）。
- 追平的标准：`scena` 的 88 个脚本全部通过 V0 到 V3，3 份测试 DAT 也全部通过，V6 通过；达到之后删除现有管线。

## 12. 风险

- **目标接口只按一种真实 VM 设计**：可能装不下未来 VM 的某些特性，比如间接跳转、跳转表、协程。V6 的测试 VM 会刻意做得和 ED9 不同，但仍然代替不了真实的 ED12；拿到 ED12 的规格时，要先对照第 3.2 节检查一遍。
- 原型可能会发现，"平坦 IR + 结构化 IR"表达不了现有三层管线能处理的某些情况；第 9 节就是为了在推倒之前把这类问题找出来。
- `name_hash` 和调试信息的语义未知：原样保存能保证完整，但以后编译器在修改之后要重新生成它们，就需要知道生成规则。
- 改为按值类型比较 Raw 之后，两种设计都可能冒出新的失败。
- 两种设计下，都还有 0.34% 的基本块没有被检查器跑到。
