# 工具链完善方案（基于现有代码渐进改造）

状态：已确认，按阶段实施。每个阶段开始写代码之前都要先确认。

## 1. 目标

在现有三层管线（LLIL → MLIL → HLIL → TypeScript）上渐进改造，始终保持 `scena` 22,118 个函数全部通过差分检查，最终达到：

1. **每一层都完整**：解析器、指令层、LLIL、MLIL、HLIL、TypeScript 每一层都满足信息契约（第 3 节），并且行为和字节码等价。
2. **最底层可以往返**：`.dat` 解析后写回逐字节相同；每个函数的指令重新编码逐字节相同。
3. **支持多种 VM**：`ir/` 和 `codegen/` 里不再含有 ED9 的概念，ED9 只通过目标接口接入；用一个测试 VM 证明换 VM 时核心不用改。

最终用途：反编译出的高级语言供人工修改，再编译回 VM 字节码，并且编译时可以面向不同的 VM。本方案只完成反编译部分，但每一层都为逆方向留好接口。

权威依据：`falcom/ed9/spec/vm_spec.md`（已逐条对照 `ed9_crack.exe` 的汇编核对）、`falcom/ed9/vm_values.py`、`tools/diffcheck` 的字节码参照解释器，以及 `scena` 的 88 个脚本和 3 份测试 DAT。

## 2. 范围之外

这一轮方案不做的事，以后单独安排：

| 不做的事 | 原因 |
| --- | --- |
| 编译器（IR 下降到指令、高级语言前端） | 先完善反编译；本轮只为每一层留好逆方向接口 |
| 可读性改进（去掉临时变量等） | 要先保证每一层完整、验证工具就位，改可读性时才不会悄悄丢信息 |
| `scena` 以外的目录、133 个解析失败的文件 | 暂时不看 |
| 名字和枚举数据 | 仓库里没有数据来源 |
| TypeScript 里怎么表示文件级元数据 | 原则是 HLIL 完整即可，输出格式等做编译器时再定 |
| 调试信息的生成规则 | 原样保存即可保证完整；生成规则到编译阶段再研究（`name_hash` 已确认可由名字计算） |

## 3. 信息契约

### 3.1 必须保存的信息

| 范围 | 内容 |
| --- | --- |
| 文件 | 文件头字段 `dword_14`；全局变量表（名字、类型） |
| 函数表 | 顺序、名字、`name_hash`、`is_common_func`、`byte06`、参数标志（32 位原值）、带类型的默认值 |
| 函数 | 调用调试信息原样保存，包括参数个数为 0 的条目 |
| 代码 | 行为；行号及其字节码地址；`DEBUG_LOG` 的值；Raw 和整数的区别；常量的精确值 |

### 3.2 可以重新生成、IR 层不保存的信息

代码和栈的布局（偏移、标签、栈槽、从未被读到的栈上值），调用序列中固定的压栈（`PUSH_CURRENT_FUNC_ID`、`PUSH_RET_ADDR`、`PUSH_CALLER_FRAME`），字符串和各种表的布局。走不到的死代码只在解析器和指令层保存。

## 4. 阶段

每个阶段的流程：确认 → 实现 → 对有变化的函数做增量检查 → 回归 3 份测试 DAT → 单元测试 → 提交并推送到 `goal/scena-diffcheck`。测试单进程运行，日志不屏蔽。

| 阶段 | 内容 | 验收标准 |
| --- | --- | --- |
| 0 基础设施 | 解析器改成先把整个文件读进内存；检查器加上导出（`--dump`）和增量检查（只检查输出有变化的函数）；实测单进程全量耗时 | 输出和检查结果都和改动前完全相同；拿到新的耗时数据 |
| 1 信息契约和审计 | 信息审计工具：从解析器模型、原始字节和每一层 IR 提取契约中的每一项并逐项比对；负面测试。现有差异先记成基线 | 能复现已知的全部差异；负面测试都能检出 |
| 2 解析器 | 修两个 bug（全局变量名、参数个数为 0 的调试信息）；写出器，原布局写回逐字节相同；`tmp/dat_audit.py` 转成正式的独立字段审计 | 88/88 个脚本逐字节往返；解析器审计零差异 |
| 3 指令层 | 去掉伪 `JMP`，fallthrough 由 lifter 根据 CFG 边生成；每个函数从入口线性解码到下一个函数，保留死代码；编码器 | 每个函数 `encode(decode) == 原字节`；反编译输出不变 |
| 4 模块层 | `ir/core` 加通用模块容器，ED9 的文件级元数据放在 `falcom/ed9`；转换流程改成按模块处理 | 每一层都能拿到文件级信息；输出不变 |
| 5 逐层补齐信息 | LLIL 保留 `DEBUG_LOG`；MLIL、HLIL 常量带 Raw 标记，常量折叠和类型推断按 VM 语义处理 Raw；行号改用专门节点，修复直通块丢行号；HLIL 参数带参数标志；TypeScript 后端和解析器同步；检查器严格区分 Raw 和整数 | 每一层审计零差异；收紧 Raw 比较后 22,118 个函数仍全部通过 |
| 6 逐层验证 | 检查器加 LLIL、MLIL 解释器，比较"字节码 ≡ LLIL ≡ MLIL ≡ HLIL ≡ TypeScript"；逐 pass 检查模式 | 出错能定位到具体的层和 pass；负面测试定位正确 |
| 7 目标接口 | `ir/core` 定义目标接口：值语义（由 `ConstantFolder` 推广）、存储模型、调用模型、元数据 schema、后端书写提示；ED9 在 `falcom/ed9` 实现。按类别迁移：值语义 → 存储 → 调用 → 字长；检查器的 HLIL 解释器和 TypeScript 解析器同步 | `ir/`、`codegen/` 不 import 目标包、不出现 ED9 专用名字（自动检查）；每迁移一类输出不变 |
| 8 证明可以换 VM | 只用于测试、刻意和 ED9 不同的小型 VM 目标，只实现目标接口 | 测试 VM 通过往返、审计和行为检查，核心零改动 |
| 9 最终验收 | 单进程跑 `scena` 全量 | 每一层审计零差异；22,118 个函数整条链全部通过，块覆盖率不低于 99.66%；输出变化都能解释 |

## 5. 已确认的事实

- 现状：22,118 / 22,118 通过，块覆盖率 99.66%。
- 信息丢失的位置：解析器 `_read_global_vars`（全局变量名多读 4 字节，5 个全错）、`_read_functions`（跳过 112,461 条参数个数为 0 的调试信息）；`llil_to_mlil.py:133`（Raw）；`mlil_to_hlil.py:770-776`（参数标志）、`922`（直通块行号，至少 572 个）；lifter 中 `DEBUG_LOG` 直接 `pass`。
- 57,671,870 字节中 99.997% 能被已知结构解释，其余是填充零和函数范围内走不到的指令。最大的 3 个脚本中，2,587 个函数代码连续，线性解码能覆盖死代码。
- 伪 `JMP`：反汇编器拆分基本块时在 `offset - 1` 插入长度为 0 的 `JMP`（最大 3 个脚本中 595 条），原因是 lifter 依赖每个块以跳转结尾。
- ED9 概念分布在 `ir/`、`codegen/` 的 29 个文件；检查器和 TypeScript 部分另有 39 处依赖 ED9 专用的 HLIL 节点。
- 已有扩展点 `ConstantFolder` / `ED9ConstantFolder`。
- I/O：直接读文件时 `c0000` 解析 10 分钟未完成；先读进内存约 6 秒完成解析和反汇编。
- 第 0 阶段完成（`c9d6c35`）：解析器改为从内存解码后，`t3400` 单进程检查从 230.5 秒降到 54.4 秒（反汇编 1.4 秒，反编译 21.2 秒），判定不变；上一轮全量各脚本检查耗时合计 7.2 小时（4 进程并发时测得），按同一比例估算，单进程全量约 1.7 小时。`--changed-since` 跳过输出不变的函数，`debug.dat` 无变化时只需 16 秒（反编译耗时）。

## 6. 保留的假设和残余风险

- 修完 I/O 后单进程全量耗时未知，第 0 阶段实测；仍然太慢则平时只做增量检查。
- 严格区分 Raw 后可能出现新的失败，在第 5 阶段逐个修。
- 第 7 阶段改动面最大（29 个文件），按类别拆分，每一步都有审计和差分检查兜底；字节码解释器属于目标层，不迁移，检查的参照始终独立。
- 测试 VM 不能完全代表未来的真实 VM；拿到新 VM 规格时先对照目标接口检查，核心可能需要补通用能力（间接跳转、跳转表等）。
- 三层结构和六次转换都保留，信息漏传靠逐层审计兜底。
- 仍有 0.34% 的基本块（1,904 个，441 个函数）没有被检查器跑到，最多的是 `debug.dat FC_Event_PartySet`（613 个）和 `system.dat GetMapEnvironmentID`（329 个）。
- 已知且在契约之外的差异：浮点 `-0.0` 的分支判断、VM 记录操作数类型错误之后的执行路径。TypeScript 的文件级元数据格式未定，TypeScript 层只审计代码项。
- 逐层检查使全量单进程耗时约 7 小时，时间集中在少数大函数；检查器尚未做性能优化，也不输出逐函数耗时。

## 7. 关键决策

- **否决推倒重建**：重建独有的收益只有"转换次数减少、L2/L3 共用节点"，有逐层审计时价值有限，代价是开发成本和重新验证 22,118 个函数。
- **先完整性、后目标接口**：迁移节点类时审计和逐层验证已经就位，丢信息能立刻发现。
- **基础设施最先**：后续每一步都依赖快速验证，I/O 修复本身不改变输出。
- **死代码只在解析器和指令层保存**：底层往返需要它，IR 层不需要。
- **调试信息原样保存**：推导规则目前不成立；`name_hash` 也原样保存，并核对它等于由名字计算的值。
